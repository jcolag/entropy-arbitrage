* Ignore for ToC

As most readers here probably already know, I spend Thursday evenings on the blog digging through an episode from the [*Star Trek* media franchise](/blog/tag/star-trek).  Starting in [February 2025]({% post_url 2025-02-06-ship-in-bottle %}), those posts began including what aired on "sibling productions" at around the same time, to (I hope) give some context to what the writers might have had in mind in the script.  In my eyes, it made a reasonable compromise between watching each show entirely in isolation (scrubbing the context, but easier to keep track of everything) and watching chronologically as we did at the time (better context, but would require me writing season-summary posts back-to-back).

![Wikidata's logo](/blog/assets/Wikidata-logo-en.svg "Jumping the proverbial gun a bit, I guess, since Wikipedia doesn't get a mention for another couple of paragraphs...")

To date, I have done this in brutally manual ways, looking up the release dates of episodes and comparing the dates visually.  It shocks me that I managed a year and a half without missing something critical, really.

Recently, though, I finally realized a few things in a useful order.

- Wikipedia has a page for every episode in the franchise, I suppose inherently Notable (in the Wikipedia sense) because an entire cottage industry exists summarizing and reviewing episodes for fans as they come out, providing plenty of Reliable Sources.  Other shows, they might have episode summaries on the series page, but you won't see each episode of **Three Moons over Milford**---the most obscure show coming to mind---getting its own article anytime soon.
- Each Wikipedia entry about a television episode (and most other things) has an informational box with some dry information, such as directors, episode numbers, production numbers, and (relevant to us) air dates.
- Those boxes get generated from data in [Resource Description Framework](https://en.wikipedia.org/wiki/Resource_Description_Framework) format.
- The Wikimedia Foundation maintains all its RDF data on [Wikidata](https://www.wikidata.org/wiki/Wikidata:Main_Page), which has a query language.
- Wikidata has a specific category code for [*Star Trek* episode](https://www.wikidata.org/wiki/Q61220733) and similarly interesting groupings.

And there we go.  Rather than scramble to figure out what episode aired when, but only the episodes that I cared about in a given week, each week, I could get a list of every episode in the franchise (as of today) with the information that I need---and probably add the films later---and pull the information from there as I need it, maybe even pulling the information out by script as I need it.

This post walks through (well, summarizes, because nobody wants to hear about the dead ends and frustrated grunting) that journey, under the assumption that either I'll need to do this again for some other project, or somebody else might need to do something similar.

## SPARQL

The [SPARQL Protocol and RDF Query Language](https://en.wikipedia.org/wiki/SPARQL) provides the ability to search and modify that aforementioned RDF content.  For those of you who have done database work, but can't make sense out of that, you can probably best think of SPARQL as the equivalent of SQL for a graph (rather than relational) database.  Each element (the RDF entry) defines its relationships by pointing to the relevant categories, building a directed graph.

If you don't do much database work, then you might get lost in the post until I start talking about CSV files.  Early on in the blog, I did write a [broad post on databases]({% post_url 2020-04-05-database %}) that might help, but I also haven't looked at the post in six years, so also wouldn't swear to it.

After digging around, I largely discovered that some of a query looks fairly conventional.  Some looks like boilerplate, probably different for each database server.  And then some oddities come up.

I won't actually try to *teach* it, because Wikidata has a fairly complete [SPARQL tutorial](https://www.wikidata.org/wiki/Wikidata:SPARQL_tutorial).  Instead, I'll skip my trial-and-error work and show what I ended up with.  I did, however, add "bad" comments, the sort that explain the elements instead of explaining why, figuring that'll help people who haven't worked with SPARQL before more.

```SPARQL
SELECT DISTINCT ?item ?itemLabel ?showLabel ?seasonLabel ?seasonNumber ?episodeNumber ?pubDate WHERE {
  SERVICE wikibase:label { bd:serviceParam wikibase:language "[AUTO_LANGUAGE],mul,en". }
  {
    SELECT DISTINCT ?item WHERE {
      # P31 follows an instance-of relationship, which we name.
      # https://www.wikidata.org/wiki/Property:P31
      ?item p:P31 ?instanceOf.
      # P279 follows a subclass-of relationship.
      # https://www.wikidata.org/wiki/Property:P279
      # We want instances of Star Trek episode, here.
      # https://www.wikidata.org/wiki/Q61220733
      ?instanceOf (ps:P31/(wdt:P279*)) wd:Q61220733.
    }
  }

  OPTIONAL {
    # P179 follows a part-of-the-series relationship.
    # https://www.wikidata.org/wiki/Property:P179
    ?item p:P179 ?seriesStmt.
    ?seriesStmt ps:P179 ?show.
    # We want instances of a television series, along the way.
    # https://www.wikidata.org/wiki/Q5398426
    ?show wdt:P31/wdt:P279* wd:Q5398426.
    # P1545 looks for a series-ordinal property, the episode number.
    # https://www.wikidata.org/wiki/Property:P1545
    OPTIONAL { ?seriesStmt pq:P1545 ?episodeNumber. }
  }

  OPTIONAL {
    # P4908 follows a season relationship.
    # https://www.wikidata.org/wiki/Property:P4908
    ?item p:P4908 ?seasonStmt.
    ?seasonStmt ps:P4908 ?season.
    ?season rdfs:label ?seasonLabel. FILTER(LANG(?seasonLabel) = "en").
    OPTIONAL {
      ?season p:P179 ?seasonSeriesStmt.
      # P1545 looks for a series-ordinal property, the season number.
      # https://www.wikidata.org/wiki/Property:P1545
      ?seasonSeriesStmt pq:P1545 ?seasonNumber.
    }
  }

  # P577 looks for a publication-date property.
  # https://www.wikidata.org/wiki/Property:P577
  OPTIONAL { ?item wdt:P577 ?pubDate. }
}
ORDER BY ?showLabel xsd:integer(?seasonNumber) xsd:integer(?episodeNumber)
```

You fill that in on Wikidata's [Query page](https://query.wikidata.org/) and click the *Execute Query* {% emoji play button %} button.

The `OPTIONAL` bits could possibly stand some simplification because *Star Trek* has such thorough coverage at Wikipedia that few if any items have data missing, but any other show, you'd definitely want the database engine to skip anything that it can't find.

Annoyingly, I can't find a way to remove `?item`---the actual found object---from the results.

Aside from that, the query page nicely lets users export the data in a variety of formats, including RDF, JSON, and CSV.  I went with CSV for this particular use, because I use fairly generic shell scripts to manage a lot of that corner of the blog, and "sort this list of JSON objects" takes more than a bit of work in Bash.  And see the next section for cleaning this up.  I saved RDF and JSON files as well, in case I want to do something more sophisticated later that could benefit from more structured data.

Searching for all episodes of a single series looks similar, but simplifies the search for matching items (the first chunk of the query) to only a part-of-the-series for the series in question, then removing the `OPTIONAL` parts that a single series wouldn't care about.  In fact, for that, Wikidata even has a [Query Builder](https://query.wikidata.org/querybuilder/) (fill in the fields with English, not the Wikidata codes) that you can use to work out the core request, before you start working out how to get the properties that you want.

## Commas, Commas, Everywhere

Good news and bad news, I guess.  For the good news, because CSV stands for "comma-delimited values."  Almost everybody running a Linux-or-similar computer probably already knows how to use tools like `cut` to pull relevant (column-wise) information from a CSV file.  For example, the following would return the first, third, eighth, and second columns.

```
cut -f1,3,8,2 -d',' whatever-file.csv
```

For the bad news, though, this doesn't always work as well as we might hope.  For example, **Deep Space Nine** has an episode titled *Treachery, Faith, and the Great River* towards the end of the run.  **Voyager** has an episode titled *Tinker, Tenor, Doctor, Spy* near the end of its run.  They don't come along often, but those commas in titles can act like columns in your CSV file, if you don't treat them correctly.

What does "correctly" look like?  Well, to the chagrin of every programmer who has ever tried to do this correctly, the closest that we have to a [CSV standard](https://www.rfc-editor.org/info/rfc4180/) serves as more of a description of what various people *tend* to do, rather than serving as a specification, and it even outright denies that you should use it as a specification, with §2 dedicated to describing seven reasons to shrug and hope for the best.

Anyway, rather than trying to figure out how to make `cut` behave (it probably can't) or writing custom code to do what we think that these Wikidata exports require, it makes a bit more sense to find software designed around this problem, which led me to [CSV Kit](https://csvkit.readthedocs.io/en/latest/), a set of tools for extracting data from CSV files.

Using *their* version of cut, I can do something like this to find a specific episode.

```console
cat "${episode_data}/startrek.csv" \
  | csvcut -c7,3,2 \
  | sort -u \
  | grep ",${title}$"
```

The `csvcut` piece---the reason that I bring up CSV Kit---grabs the date, the series title, and the episode title, even if some field has a bunch of commas in it.  Then, because the date now comes first, sort the results to put everything in chronological order; the dates come in YYYY-MM-DD format, so we don't need to do anything tricky to sort.  Finally, we search for the title, which I already need to generate the skeleton of the post.  Here, we make sure that we search for it only at the end of the line (the title comes last in the cut command, remember) and preceded by a comma, in case we have other situations where titles overlap, such as [*Lower Decks*]({% post_url 2025-09-04-lower-decks %}) sharing its title with an entire series, or the remarkable similarity in titles between [*The Emissary*]({% post_url 2023-04-06-emissary %}) and [*Emissary*]({% post_url 2026-02-26-emissary-1 %}).  If I didn't add the comma and end-of-line marker, that search would sometimes flag a bunch of false positives.

Instead, for tomorrow's post, this returns the (more reliable) following.

```CSV
1993-09-26T00:00:00Z,Star Trek: Deep Space Nine,The Homecoming
```

As expected, we get the air date, the series title, and the episode title for the correct episode.  And if I search for *Lower Decks* or *Emissary* that way instead, then I get the right episode.

However, oops, this doesn't actually help us, because we already knew about the episode itself.  We want the episodes before and after, not the specific information that we already knew.  This only adds the information that it aired in late September 1993, and I only rarely care about that for a post, since I don't have (much of) an interest in journalism about how things went down in our world.  In that case, we can touch up the search.

```console
cat "${episode_data}/startrek.csv" \
  | csvcut -c7,3,2 \
  | sort -u \
  | grep --before-context=2 --after-context=2 ",${title}$" \
  | sed 's/^/- /g'
```

The `before-context` and `after-context` arguments do pretty much what they sound like, giving (in this case) the two lines before and after the episode that we want.  And since we sorted by air date, we now get results more like this.

```CSV
1993-09-18T00:00:00Z,Star Trek: The Next Generation,"Descent, Part II"
1993-09-25T00:00:00Z,Star Trek: The Next Generation,Liaisons
1993-09-26T00:00:00Z,Star Trek: Deep Space Nine,The Homecoming
1993-10-03T00:00:00Z,Star Trek: Deep Space Nine,The Circle
1993-10-04T00:00:00Z,Star Trek: The Next Generation,Interface
```

And *that*, I can use.  **Star Trek:  Deep Space Nine**'s *Homecoming* comes after **Star Trek:  The Next Generation**'s [*Liaisons*]({% post_url 2025-06-05-liaisons %}) and before (next week's post) **DS9**'s *The Circle*, and after that, we'd have **TNG**'s [*Interface*]({% post_url 2025-06-12-interface %}).  And notice that, before *Liaisons*, we see an example of this working even though the title of an episode has a comma in it.

Why ask for two lines on either side instead of only one?  It looks like some season and series entries made it into the list, maybe other items that I don't need.  And as I'll mention in a bit, I can envision adding other shows that might resonate with the project without affecting what I would normally have to say, so the extra context lines plans for those possibilities.

Oh, and I added that `sed` command to the end to turn those five lines into a Markdown list, adding a dash and a space in front of each line, so that Jekyll doesn't run them all on one line when I initially check the HTML version of the post to start writing.

## Expansion

This gets better, because now that I have every episode so far (and only need a subset of what I have), I can create additional files with the films or even other franchises.  Adding them to the list of files sent to `cat` puts them in the right position in the results---assuming that I don't mess up the columns---because sorting in chronological order works the same across files.

What might that include?  Well, those of us old enough to have watched these shows on television might recall that the middle of **DS9**'s second season (the post going out in mid-October) needed to deal with competition from a similarly syndicated science fiction series running on another network, which bore many superficial similarities.  Knowing that an episode landed after a critical run of the other show could indicate reacting to it.

Admittedly, I don't know if I'll ever need to do this sort of work again, but the next time that I have a one-off idea that could benefit from having a table of all known exoplanets---a real example from last year that I only remembered wanting now, and don't remember why---or programming languages, I can start with the query builder to look for instances of [exoplanets](https://www.wikidata.org/wiki/Q44559) or [programming languages](https://www.wikidata.org/wiki/Q9143), and have that ready to go fairly quickly...as long as the Wikimedia community finds it important enough to fill out.  You might note that my two examples already show what I mean by priority, that category for programming languages has a much lower number in its identifier (meaning that they created it significantly earlier) than the category for exoplanets.  Some categories will have incomplete information, others maybe inconsistent depth of coverage.
