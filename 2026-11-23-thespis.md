## Recipe

Not really a recipe in any meaningful sense, but in case it comes in handy for someone, I ran some experiments popping popcorn.  I have largely held a low opinion of popcorn, but someone signed me up for a grain-of-the-month club (as far as I can tell) a while back and have had a fancy-looking bag giving me stink-eye for a few months.

The traditional approach of popping corn in a skillet flopped completely, the oil smoking heavily with nothing happening to the test kernels.  The theory?  Before those ungainly popcorn poppers became common, if you had loose popcorn, you'd leave a couple of kernels in an oiled pan (covered) over heat.  When either of those kernels popped, you took the pan off the heat to add the full load of kernels, give the heat some time to work through the corn, and return the pan to the heat, at which point you'd get fairly rapid popping.  This didn't, for whatever reason.

The next trial went for the air fryer, covering the grate at the bottom of the tray with aluminum foil.  Running it at 400°F (205 C) for eight minutes with two teaspoons of kernels worked, giving me about a quarter-cup of popcorn, but made a bit of a mess with popped kernels trying to work their way under the foil or escape the tray entirely.

Trying to solve that, I tried building the kernels a little packet about the size of the popped corn, but that flopped.  That makes sense, because air fryers cook by convection; wrapping the food eliminates the air flow---the convection currents---meaning that it'd need to cook longer and at a higher temperature, the latter increase impossible.  Undoing the packet and going with the grate cover (with the same kernels) still worked, though.

The verdict?  I still have a fairly low opinion of popcorn---the flavor doesn't measure up to the smell while it pops---but if I need a light but warm snack, I could do worse while I use up the bag.

## Clearer Licensing, Part 5

To recap the point of this exercise, the public licenses that I use all include an attribution requirement to some extent.  And while the AI industry continues to use its software to launder copyright as "intelligence," it has started to make sense to make a bigger stink about that attribution.  To make this as convenient as possible, I chose the [REUSE](https://reuse.software/) standard that I have used elsewhere, since it ensures that every file has attribution and licensing information; going file by file also nicely resolves some common edge-cases, such as when I include a file from someone else's project or when worrying about whether anybody has the right under the AGPL to see the alterations to a configuration file, revealing API keys and passwords.

This time through, I got the following into shape.

- My old [Wierd](https://codeberg.org/jcolag/Wierd) programming language.
- My similar-vintage [Klickenklacker](https://codeberg.org/jcolag/klickenklacker) programming language.
- The [URL Rat](https://codeberg.org/jcolag/url-rat) browser plugin.

With any luck, I'll have a REUSE-specific post ready soon.

## Serĉteamo

{% codeberg jcolag/sercxteamo %}

I have teased this project for a while, so it probably won't surprise too many regular readers to know that I finally stopped dithering and quietly kicked off the Serĉteamo project.  It has two major goals.

Most directly, it'll try to reimplement the communications protocol used by [YaCy](https://yacy.net/).  If you have followed these developer diary posts where I have written about building and improving my [mini-servers](/blog/tag/mini-server), then you might recall that I had a lot of optimism for YaCy, a distributed search engine with a peer-to-peer search index created by the users.  It returns pretty good search results, but I have found it difficult to run for any significant length of time.  And the development community spooks me a bit, sending people to ChatGPT for support, spending time on adding an AI chatbot to the search interface, and even letting AI write the code, and that inability to "read the room" makes me wonder if the instability that I see comes from vibe-coding twenty-year-old Java software.

As other people have said about various projects, if an open protocol only has one implementation, then you can't really call it an open protocol, because people don't have an exit strategy if the implementation starts breaking.  Therefore, it all started adding up in my eyes that we need more software using the same network.

As a quieter goal, long-time readers will know that I have spent a lot of this year thinking about what the software industry probably, especially Free Software, needs to look like after the AI bubble bursts, and I want Serĉteamo to figure out what delivers better software so that we can model those good processes.  Unsurprisingly, the project won't permit AI-generated contributions[^srdprk], instead having a couple of tricks up its sleeve to focus on quality instead of lines of code.

[^srdprk]:  I hesitate to use that term, because it doesn't actually *contribute* anything to the project to ask a chatbot to extrude out some plausible-looking code for you without any consideration to maintainability or even fitness for the purpose.

To start, that means [literate programming]({% post_url 2026-11-18-literate %}) (hence last Wednesday's post), formal verification where possible, and automation of each test as we create it.  I chose [OCaml](https://ocaml.org/) provisionally because people generally rank it as having a high expressivity, we can tap into existing work to model programs using [Rocq](https://rocq-prover.org/) for verification, and it has a compiler that produces native code.  Literate programming focuses attention on the human factors of design.  Formal proofs give us confidence that the code will do what we expect.  Automating tests means that human testers can focus on looking for potential new problems instead of wasting time following a script.  Expressivity reduces the opportunities for bugs.  And native code should help minimize the load of keeping the software running.

I don't believe that those features alone can close the gap between the growing complexity of code and the amount of time available to verify things, but we need to start somewhere.

At this point, significantly less lofty than the goals, the repository only has the README file, a code of conduct, and contribution guidelines---plus the relevant licenses---in place.
