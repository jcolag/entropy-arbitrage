* Ignore for ToC
{:toc}

Long-time readers know that, a while back, I ran across the [REUSE](https://reuse.software/) page and immediately saw value in the standard.  It has mostly become a standard part of my workflow, especially for new projects.

![An abstract design with curved tendrils flowing into circles](/blog/assets/oli-maia-2017-010.png "What, did you want a photograph of somebody literally reusing a thing...?")

I have found the documentation fairly bland, though.  More than that, I have run across a bunch of glitches that nobody else seems to talk about.  Between the two, it made some sense to put together a post.  I can't guarantee that this contains everything that I know, but it definitely contains everything that I remember knowing.

## Concept

For those not familiar with the idea, REUSE requires that every non-ignored file in a repository have a clear copyright statement---year and owner---and the [SPDX identifier](https://spdx.org/licenses/) for the license granted to users of the file.

To make it possible for software to extract and use the information reliably, each of those two pieces gets a label for clarity, so you end up with (usually) comments that look like this.

```c
/*
 * SPDX-FileCopyrightText: 2026 John Colagioia <john@colagioia.net>
 *
 * SPDX-License-Identifier: AGPL-3.0-or-later
 */
```

Before seeing this, like everybody else, I would leave a `LICENSE.md` file or similar in the repository and move on, but I see this standard as handling a few separate issues.

- Most prominently, if a file gets separated from the overall project for whatever reason, then that file often loses its attribution and licensing information.
- When a project uses a file from another project, we don't generally need the full provenance, but we *do* need to know if its licensing differs from the rest of the project and probably want to know who created the original version.  This especially might matter when a project needs a proprietary file---such as a logo---in the final application to comply with a platform's rules.
- If a project's license requires publishing changes to server-side code---such as the AGPL---then one could plausibly argue that a server's owner has modified or adapted the default configuration file and so must release the changes, which might include passwords and API keys, among other secrets.

If every file states its own license, then these problems no longer exist.  A separated file includes the relevant information.  Files borrowed from other projects have different copyright and licensing information from the rest of the project.  And we can cleanly provide default configuration (and similar) files with a license that carries fewer obligations, without resorting to a note in documentation that nobody will read.

I believe all my new projects since discovering it follow REUSE.  However, I have started applying REUSE to old projects, too, largely because of AI's endorsement of plagiarism.  Even if the entire AI industry would vanish tomorrow---not entirely impossible, mind you, as we see export violations funding the circular financing, alongside hoarding computer hardware to drive up prices, destroying employment numbers, making infrastructure fragile, stocks crashing, and more all coming out at the same time---they have still normalized the idea that code provenance doesn't matter, and I believe that we need to fight that, starting with making attribution as clear and convenient as possible.

## Annotations

You *can* do this manually, if you want:  Create a `LICENSES` folder that includes a copy of each license used, named for its SPDX identifier, then add the `SPDX-FileCopyrightText` and `SPDX-License-Identifier` comments to each file.  However, that gets tedious, so the `reuse` command makes this more convenient.  They built it in the vein of a multi-tool with a variety of commands available.

For this purpose, the `annotate` command adds the information, assuming that it can identify the style of comments required for that file.  For example, I frequently run something like this.

```console
reuse annotate \
  --copyright='John Colagioia <john@colagioia.net>' \
  --license=AGPL-3.0-or-later \
  --year=2026 \
  *.js
```

You provide your identity (with or without an e-mail address), the license, and the year, and the tool tries to populate the files.  Alas, it has some snags to watch out for.

- If it can't properly identify *any* file in your list, it abandons the entire task, instead of doing what it can and reporting the failures.
- Older versions of REUSE called this command `addheader`.

That difference in versions feels like it shouldn't matter much, but it does mean that I needed to adjust a couple of scripts that I wrote a few months ago.  Worse, different platforms offer *wildly* different versions of REUSE; my operating system couldn't get anything recent until I caved and went the Python route.

```console
pipx install reuse
```

Also, sometimes it gets the header wrong.  That has come in two forms for me.  First, because everybody has somehow decided to use file extensions to identify file types---even though {% wiki File_format#Magic_number|magic numbers %} and other analytical techniques have existed for something like forty years---and some file extensions have unrelated uses, so it uses the wrong style of comments.

Second, it has no way of understanding when a file has two parts, one of which needs to come first.  For an example that some readers might have noticed, when I applied REUSE to the blog's code, it inserted the comments before the YAML metadata in the various layout files, making them unusable.  If you look in the commit history for the blog, you'll see a series of changes where I noticed that the [search](/blog/search), the [calendar](/blog/calendar), or whatever page stopped rendering properly and so moved the comments *after* the metadata.

One really nice new(?) feature, annotate supports a `--contributor` option.  If, for example, I write some code and you commit changes to it, then your name should get listed, too.  I like this, because it makes the contributors readily apparent, which certainly makes properly crediting the team more convenient.  However, it also streamlines the rare times when someone wants permission to change some code's license, either to include in a project under an incompatible license or to change the license of the entire project; one hopes that a list of all contributors deters the latter by showing the scale of the people required to buy in.

### Ride-Along Licensing

Meanwhile, as mentioned, REUSE won't recognize some files at all, so they need extra handling.  It looks like the current version has changed those options, and included a useful version that---if anybody wanted to ask me---they should have made the default behavior:  If it can't identify the kind of comments to use, the `--fallback-dot-license` option creates a *new* file with the same name plus a `.license` extension with the copyright and license information.  Older versions of REUSE only have `--skip-unrecognised`, which still exists, and does what it sounds like.

Incidentally for Americans, note the British-only spelling in the latter option.

### INI-ish

Oddly, REUSE has added a *third* place to put licensing information in recent versions, which probably does work better for some uses, but also starts to defeat the purpose if you need to look around for licenses.  Anyway, you can also create `REUSE.toml`,  which can contain license information for any files where you might not want (or can't have) the comments or a separate file for everything.  It looks something like this.

```TOML
version = 1

[[annotations]]
path = ["README.md", "CONTRIBUTING.md"]
precedence = "aggregate"
SPDX-FileCopyrightText = "2026 John Colagioia <john@colagioia.net>"
SPDX-License-Identifier = "AGPL-3.0-or-later"

[[annotations]]
path = ["config.json"]
precedence = "aggregate"
SPDX-FileCopyrightText = "2026 John Colagioia <john@colagioia.net>"
SPDX-License-Identifier = "CC0-1.0"
```

As an example of where I probably *should* use a file like that, consider the [blog's assets](https://gitlab.com/jcolag/entropy-arbitrage-assets).  Because it contains every image, the fonts, and a handful of miscellaneous files such as music and documents, it looks like a mess.  I can't insert comments into the files---most don't contain any text---and adding thirty-five hundred `blah.png.license` files (plus a couple more every week) makes the mess worse.

Right now, I "solve" this problem by running a script that pulls the *Credits* section of every post to generate a monster `LICENSE.md` file that provides the source post, the file, relevant attribution, and the license as an ugly bulleted list.  However, I could make the script a bit smarter to have it generate a baseline version of the TOML file with more elements (title, source URL, etc.) for each `annotations` block, instead, then add new sections as the blog adds images for posts, making that information more useful to people who stumble on the assets-only repository.  In fact, I probably wouldn't actually ever do such a thing[^Uvw-7s], but in theory, I could potentially even stop writing the bespoke credits for each post and query `REUSE.toml` for the relevant information for each file referenced by the post.

[^Uvw-7s]:  The "ritual" of attributing everybody else's work seems too important to the project to automate it away, and it rarely takes any actual effort, considering that I almost always have all the information in front of me when I choose an image.

Bear in mind that you don't need to worry about any file caught by a `.gitignore` file, at least in theory.  More on that later.

## The Legalese

When you know what licenses you need, or as you recognize that you need one---you can run these steps in whatever order works for you---the REUSE tool handles that, too.  Take a quick example.

```console
reuse download AGPL-3.0-or-later CC0-1.0
```

Again, everything uses those SPDX codes to identify the license.  You name them when downloading that way, and it downloads them to files by that name in the `LICENSES` folder.

If you somehow need a list of all the supported licenses (currently seven hundred forty of them), you can get that.

```console
reuse supported-licenses
```

It seems easier to check the SPDX page, but I suppose that having the information at your fingertips might help, too.

### Exceptions

I should mention one (seemingly undocumented) "hack," here, dealing with files *not* released under Free Culture licenses.  One of my repositories---I forget which one---includes the Buy Me a Coffee logo, in case anybody wants to (might as well link) [kick in some money to me](https://buymeacoffee.com/jcolag), and I can't claim that it comes under some more appropriate license.  Someone on the Fediverse, I vaguely remember, similarly complained about one of the video game consoles requires displaying the (proprietary) platform logo or something similar to get accepted, wondering whether distributing a Free Software game for that platform would violate the GPL by withholding a file technically needed for the build.

I forget where I tracked it down, and I can't guarantee that it'll always work with REUSE, but [SPDX allows for other licenses](https://spdx.github.io/spdx-spec/v2.3.1/SPDX-license-expressions/) by giving them a `LicenseRef-` prefix.

> a user defined license reference denoted by the LicenseRef-`[idString]`; a license identifier combined with an SPDX exception; or some combination of license identifiers, license references and exceptions constructed using a small set of defined operators (e.g., `AND`, `OR`, `WITH` and `+`).

In the case of a proprietary file, I created `LICENSES/LicenseRef-Proprietary.txt`, which only says the following.

> All rights reserved under relevant copyright statutes.  Used with permission.

It could probably add a link to the page where it explains the permission, but I don't know if that makes a huge difference like it would if asserting that somebody had released an older work under a Free Culture license.  Then, the Buy Me a Coffee logo has a license file that uses it.

```
SPDX-FileCopyrightText: 2024 Buy Me a Coffee

SPDX-License-Identifier: LicenseRef-Proprietary
```

I mentioned that I can't guarantee that it'll work permanently, because this does seem to violate the spirit of REUSE to carve out exceptions for proprietary material.  It wouldn't surprise me if some future version complains about non-OSI-approved licenses or something similar.

## Checking the Work

What do we mean by "work," here?

The same tool for downloading the licenses and adding the header comments can also check your work.

```console
reuse lint
```

That responds with a report of any licenses referenced by a file that you haven't downloaded, files without copyright information, files without a license statement, and files without either copyright information *or* a license statement, plus a summary of the current state of the project and whether the repository complies.

In theory, it skips any file that you version control system's ignore file, such as `.gitignore`.  In practice, though, it seems more complicated, somehow.  One of my repositories, in not-yet-released code, it somehow refuses to honor the ignored set of files, and I haven't yet figured out what makes it different.  All other repositories, though, seem to behave normally.

The linting also has a `lint-file` variant that (no surprise, I imagine) only checks the status of a single file.  I don't know *why* you would do that, but the option exists.

Related to linting, you can also generate a bill of materials.

```console
reuse spdx
```

That includes the file's name, an ID, a checksum for the file, the license, and...it gets weirder from there.  Each file's entry also has a [license concluded](https://spdx.org/rdf/spdx-terms-v2.0/objectproperties/licenseConcluded___-571936219.html) field for apparently cases where we need to guess at the file's actual license, concluded as in "came to a conclusion."  And it also *tries* to include the copyright text, but I'd call it buggy, in that it appears to grab every line in the file with the word *Copyright* capitalized.

## Recycling

I think that covers everything that I have worked out over the past maybe-two years that I have applied it to projects.  As I mentioned and have (I hope) sufficiently explained, it still has some rough edges, but I think that the value to a complicated project warrants figuring out how to live with those pitfalls.
