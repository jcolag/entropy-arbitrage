## Mini-Server, Part 31

It took me a long time to put in the effort, but I finally installed [Pi Hole](https://pi-hole.net/) on one of my servers.  If you couldn't guess, I put this off because it seems like a lot of work, and...yeah, it does, in fact, require quite a bit of effort.

Quick verdict after about a week?  If you have the capacity, and if you'll always have someone available to fix unnecessarily blocked sites---I'll explain what I mean at the end---then I would call it worth the effort.

### My Kingdom for a Sensible Router

First, the target machine needs a static IP address on the local network.  Checking my router's configuration page, it doesn't have anything related to DHCP, so (because the ISP owns it) I contacted support.  They, predictably, gave me the runaround.  "Static IP addresses only come with (some) business accounts."  "Control of DHCP requires extra security" (huh?).  And "you could plug a commercial router in and manage that."  Oh, gosh, I have their *permission* to spend more money on top of my monthly bill?  Thanks, I'll take that into account[^BYFtyb], the next time a competitor comes to my door.  I strongly suspect that the tech served as a conduit for some useless chatbot.

[^BYFtyb]:  I should probably use my own router, but don't feel like buying more computer equipment for that corner, and the handful that I already own, I've had for so long that they could probably get driver's licenses, which would presumably impact speed.

Anyway, poking around their web interface---which I guess won't work if the connection goes down?---I *did* find an "IP address distribution" range, which I suppose *passes* for DHCP reservation except that I need to maintain a spreadsheet of used IP addresses instead of letting the computer do that.  Fine.  Whatever.  I clear some space on the network, and...

### Staking the Claim

Wow, we can't have a quick command to say "make this the fixed IP address," I guess.  Instead, I get to have fun with this nonsense (on Debian).

```console
sudo nmcli connection
# The connections have names, and we need the name of
# the correct network, based on the type and device.
# In the following, I call that the-network-name
# XX.XX.XX.XX serves as the placeholder for the intended
# IP address.
sudo nmcli connection modify 'the-network-name' ipv4.address XX.XX.XX.XX/24
sudo nmcli connection down 'the-network-name'
sudo nmcli connection up 'the-network-name'
```

Well, wait, *that* won't work.  Logging in through an `ssh` connection, when the network connection goes down, so does my access, so I can't do that.  Instead, armed with the network name, I put those two lines into a quick shell script, and ran that in such a way that it'd continue after logging me out.

```console
nohup sh reset.sh &
```

That (I hope) gives me a persistent IP address to work with.

### Forgetting Why I Walked in Here

Finally, I get to actually install the Pi Hole software.  That goes through without a hitch.  Run the script.  It installs.

At the end, it happily informs me to hit `http://ip-address:80/admin`[^8MMloU] to check out the dashboard.  And that seems like an interesting idea, except that I already use these servers, so they all have (NGINX) web servers of their own, sitting on (HTTP) port 80.

[^8MMloU]:  Alternatively, it suggests `http://pi.hole:80/admin`, but it *definitely* didn't set up that alias, nor does my network recognize the fake `.hole` top-level domain, making that silly.  It seems especially silly when a script can do something like `dig +short -x <ip-address> -p 5353 @<ip-address>` to get the machine name on the network.

Digging around, I found a lot of obsolete instructions on how to deal with this, but few spots with the correct information.  For anybody else stuck in that situation, you want to edit `/etc/pihole/pihole.toml`.  Look for `[webserver]`.  Change the `domain` from `pi.hole` to whatever you call the machine, then change the `port` to HTTP and HTTPS ports that won't conflict with anything else that you run.  Restart Pi Hole's service, and I can now see the dashboard.

### Who Goes There

I open up my laptop's settings for the Wi-Fi network, add the Pi Hole machine's IP address as the DNS server, and...nothing.  Searching around, it turns out that Pop!_OS---yes, they still call it that---doesn't actually use the graphical interface for those settings[^RVVPR3].  Why would it, right?

[^RVVPR3]:  Why do I use it?  It came pre-installed on the System 76 laptop.  When that machine died unexpectedly, and I scrambled to replace it, to get the Framework machine (this {% emoji waving hand %} one) running as quickly as possible, I moved the hard drive over, and it has roughly served the purpose, so I haven't touched it.

Get this fix.

```
sudo systemctl stop systemd-resolved
sudo systemctl disable systemd-resolved
sudo mv /etc/resolv.conf /etc/resolv.conf.orig
sudo systemctl restart NetworkManager
sudo vi /etc/resolv.conf
```

Then the new version of the file needs to specify Pi Hole's IP address with `nameserver XX.XX.XX.XX`.  *Now*, the laptop uses Pi Hole to block ads, before the browser's ad blocker gets to it.

To explain that, we get rid of the networking service that the operating system actually uses, replace it with a different service, and *after* starting the new service, then configure it.  Somehow, that works.

### Finalizing

Back on the server, add a nightly job for the root user to run `pihole -up`, and that should work, at least until I find out that something doesn't actually preserve the IP address or whatnot.  I added some block-lists that I see people recommending and a similar allow-list for the referral networks common to mailing lists[^QgQbig], and...I'll keep the ad blocker running on my laptop, especially for if I travel, but it looks like it might not get much work anymore.

[^QgQbig]:  My ad-blocker catches those and forces me to click through, which generally protects from any malicious uses.

I should probably mention that, depending on your personal interests, you can find lists to block gambling, media piracy, pornography, social networks, and more.  Most *people* should probably substitute that sort of blocking with conversations about staying safe, but organizations that need to worry about liability might not have that option.  Anyway, if you use an ad-blocker, it looks like most of them use the same format, so you have a good chance of even using the filters that you already have.

### Course Corrections

I should note that I have needed to explicitly allow two domains since starting this up.  Apparently the GNOME Crosswords app needs `picayune.uclick.com` in order to work.  And [Spoutible](https://spoutible.com/jcolag) somehow got blocked, so I allowed it, too.  By the way, if you wondered why I didn't post blog announcements to Spoutible during the week[^cC2m9J], that explains it.

[^cC2m9J]:  Given the owner's exclusive use of freelancers on short-term gigs for software development, I actually assumed that something had gone wrong with Spoutible itself, rather than anything on my end.  I got halfway through drafting an update for this post (about how I didn't expect it to come back, and so probably wouldn't try posting there anymore), until I thought to check the Pi Hole log.

How did I know to allow them?  Things broke---the Crossword app returned errors when downloading puzzles, and Spoutible wouldn't load---so I looked under *Tools*/*Tail log files*/*pihole.log* to find what lookup failed.

Because you can't really predict what'll show up in the dragnet, as I said at the top, I'd highly recommend making sure that you always have someone available to unblock things that people might need.  For my household, that comes with the territory, since I live alone, so if I leave the house, the number of web requests that might go wrong plummets.  But if you live with other people, either everybody should have training and administrative access or somebody who they can trust to not leave them hanging.  If you have kids old enough to stay home alone, for example, you probably don't want to come home to discover that the fancy ad-blocker also blocked some application that they need for a school assignment, delaying them by however-many hours.

## Entropy Arbitrage

{% codeberg jcolag/entropy-arbitrage-code %}

As some of you might have noticed, [Thursday's post]({% post_url 2026-08-27-melora %}) hit my website about half an hour later than I had planned.  What happened?  GitHub spent most of the afternoon flaking out.  When I went to rebuild the blog, the older [developer diary posts](/blog/tag/dev-journal) that still show the fancy GitHub previews kept getting errors as they tried to get the descriptions and images for each repository.

Initially, I blamed it on Pi Hole, since it manifested as a DNS resolution problem.  But bypassing it and hitting the same problems told me that this needed a more sophisticated solution.

As an expedient solution, I caught the network error in the GitHub plugin, and created a placeholder for the link previews that couldn't find their way to GitHub itself.  It means that people will occasionally stumble across ugly previews, but it'll do for the moment.  And I don't feel too guilty about the lack of polish, considering that I so rarely need a preview link to GitHub, these days, after moving pretty much everything interesting over to Codeberg.
