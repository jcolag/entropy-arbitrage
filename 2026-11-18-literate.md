* Ignore for ToC
{:toc}

For a project that I have had in mind for a while, I realized that it would work best as {% wiki Literate Programming %}, where the source code becomes more of a design document and "construction kit" for the program---writing the program for humans---and then using tools to pull out the pieces needed to compile or run the code.  I have always liked the premise, but never had the opportunity to kick the tires.

![A Peruvian woman weaving on a loom](/blog/assets/27536467371_5b955124df_o.png "A looming complexity")

Thinking about it for the project in question, literate programming made sense for a project where I'd like to onboard people instead of working on my own, sure.  But also, as many of you know, I keep trying to think about what software development can or should look like after the AI bubble bursts, and would like to use this project in particular as a laboratory for possible options, especially if it draws collaborators.  I talked about some of those possibilities in the back-half of my post about the [Software Crisis]({% post_url 2026-03-29-software-crisis %}), but managed to overlook literate programming, there, probably because it has never seemed like a concrete opportunity.

To get moving on this, I did some quick research that pointed me to [Noweb](https://www.cs.tufts.edu/~nr/noweb/)[^nOa1ZI], a language-independent implementation of most Literate Programming concepts.  I installed it and read through the documentation, and...the documentation felt lacking.

[^nOa1ZI]:  I should note that Noweb has a weird custom public license that I don't believe would pass muster as Free Software.  Despite that, it looks better than the alternatives, and the actual tooling probably doesn't matter when we could plausibly create a new implementation without too much trouble.

In fact, every document that I could scrounge up talked heavily about the history of the Literate Programming space, and the philosophy behind it, as if they haven't already "made the sale."  They'd talk about the highest-level formatting of the file.  And they'd talk extensively about the output, sometimes including how to further process it.  Nothing really had a "how the heck do I put this into practice?" section.  And even examples---ironically, given the premise of literate programming---didn't provide enough context for me to work out the specifics.  And it seems all the more frustrating that the setup doesn't actually have more than a few pieces to care about, so acting so coy seems absurd.

Eventually, I pieced together what I needed from different sources, and I present the results here, as much so that I never need to hunt for it again as saving the next person some trouble.

## Literate Programming, Quickly

Before we get going, I should give some background on the concepts.  After all, unlike me trying to sift through documentation, *you* probably didn't seek out this post because you already had an interest in literate programming, and depending on your background, you may have never even have heard of it.  I'd guess that most readers with a software background have only heard the phrase in passing, one of many ideas and projects tying back to {% wiki Donald Knuth %}, and knowing Knuth's name, you might guess the broad idea.  Therefore, let me provide a quick and maybe-quirky overview of the premise.

When I start a project professionally, I habitually ask for the "nickel tour," a term that I have learned most people have *not* heard and can't gather from context, so there you go.  Really, I want the self-deprecating quick walk through the project of the sort that, if I paid for it, wouldn't want to pay much.  Inflation has attacked the idiom, so you'll now sometimes see [fifty-cent tour](https://en.wiktionary.org/wiki/fifty-cent_tour) in place of a nickel, assuming that you see it at all.  To sum up my intent, though, I want enough information to orient myself, but don't want to take much more of a colleague's time than that.

I think of literate programming---introduced in 1984, in case anybody wants to run down the early papers---as building the program *as* that tour, showing the program in fragments in an order most meaningful to the team and most useful to explaining how things work, and explaining why each fragment works the way that it does, along with the tradeoffs.  For a new project, it might look more like the design process[^UZdtvC], describing the thought process behind the pieces.  People often try to simplify the concept to "documentation" or "comments," but we already have both of those; we *don't* otherwise have the guided tour through the project, so that makes a better explanation for me.

[^UZdtvC]:  For those of you in software and old enough to have worked before Agile methodologies reshaped everybody's workplace, you might think of the requirements document, where the developers take each section and use it to introduce the code that fulfills that requirement.  Later sections stitch those pieces together into a working program.

You end up with something that looks a bit like pseudocode (but without undermining functionality), with many sections showing only the control flow with references to the parts to fill in, and other pieces show the parts to fill in without the surrounding control flow.  This introduces a new step in building the project, where a preprocessor pulls the actual source code from the literate program to hand to the compiler or interpreter.

Interestingly, I don't see anybody else talking about it, but I see a clear advantage here, beyond (as every write-up on this will explain) asking developers to think through the problems in print and having a pretty good onboarding tool:  By organizing code in terms of what the developers found important, you can find the sections that you need without tracing through execution, and see/edit that piece in isolation without dealing with the boilerplate code.

Knuth has claimed that he called his system "Web" because he couldn't think of many three-letter words not already in use as software packages, and pretty much retrofit the web-of-connections metaphor later.  The literate program goes through two processes that follow the metaphor, though:  You "**tangle**" the program to get the version out that you'd pass to the compiler or interpreter---think of it as undoing the clean organization---and you "**weave**" the code into the document to publish.

## Broad Syntax

The literate programming community generally talks about writing the program in "chunks," though you'll occasionally see other terms such as "macros" that...feel misleading.  We have two types of chunks.  And at least for Noweb, starting one code chunk immediately ends its predecessor, giving us less syntax to keep track of.

### Comments

*Comment chunks* start with an at-sign (`@`) and some horizontal or vertical space.  By convention, the comment chunk describes the code chunk that follows it.

```
@ comment here

comment there

@

Another comment
```

Noweb accepts comments written in LaTeX.  Or, rather, that doesn't actually describe the situation.  You write the comments in your intended output format, TeX, LaTeX, HTML, or whatever.  I'd call it pretty frustrating that you can't publish the results in all forms, but there you go.  Actually, even that doesn't tell the entire story, because it also has its own bit of markup that, if you enclose text in double-brackets---`[[like this]]`---it'll render that text in a monospaced font to indicate code, beyond what the other markup language does.

I have already implied it, but I should maybe say outright that I hate the term "comment," here.  Yes, it comments on the code, but this doesn't replace comments in the code.  If we only wanted comments, then we'd use comments.  Document-generation systems play-act at literate programming, for example, with their marked-up header comments that everybody studiously ignores, because they never say anything that you couldn't spot in the code, and frequently become wrong as people update the code and forget to nudge the comment.

### Code

Meanwhile, *code chunks* have a goofy-looking heading to give them an almost-certainly unique name, though you never know when some language will have overlapping syntax, I suppose.

```
<<Whatever Name>>=
whatever code
```

Referring to code chunks to insert them into other chunks removes the equals sign at the end, such as `<<Whatever Name>>`.  And it pleased me to discover that inserting a code chunk follows your indentation correctly in the final code, adding the indentation of the reference to each line in the chunk; if you use a programming language that cares about indentation levels, Noweb won't break it.

Maybe not immediately apparent, but the references mean that the code chunks plug into each other in a tree-like shape, with each chunk potentially using more code chunks in its flow.

Oh, and I can't (yet) envision a use for it, but code chunks aggregate through the document.  If we define a second `<<Whatever Name>>=` later, it'll append that code to this when we reference it.  That does mean keeping track of yet another set of names, so that the project doesn't accidentally get multiple `<<Sanitize Data>>=` blocks that sanitize unrelated things, because you'll get all of them in each use, rather than the one that you want.

Because a code chunk might define names for the program---think creating variables, classes, functions and methods, and so forth---you can make that explicit at the end of the code chunk with a one-line comment that includes every definition in that chunk.  Like a normal comment chunk, it ends the code chunk, explaining why it goes at the end.

```
@ %def name1, name2, and_so_on
```

You don't always need to do this part, hence it not getting explained particularly well, I guess, and probably the biggest reason that this post exists[^pcyUpL].  If Noweb can separate declarations from usage in your chosen language, whether on its own or through a filter, then it'll pick those up without needing that annotation.

[^pcyUpL]:  For the full story, every new document that I found had a passing mention that you can also identify variable definitions if necessary---painstakingly describing the difference between defining a variable and using a variable as if any reader has never written code before---and then showing an `@ %def` example as if that required no further explanation.

This can make a difference in the final document, as it tries to link the uses and definitions for convenient reading.

### Root Chunk

One code chunk defines the layout of the overall code, called the **root**.  By default, the tangling (code extraction) process presumes that it has the name `*`, but we can override it when "tangling" (extracting) the compiler-ready version of the code.

For example, as I start thinking about where I would apply literate programming, I keep thinking of the root as the boilerplate code, the lines that you probably copy from some other file or generate, because writing it from scratch can only introduce potential errors.  If we continue the idea of a literate program as the tour of the code, the root chunk would include the parking lot and exterior walls of a space, the boring parts that most people would comfortably assume exist.  In code, that would at least include file headers, required libraries, and maybe the initialization code.

Only rarely would anybody in the team need to review the list of libraries used or the boring configuration-parsing code, so it makes a good case to go in the root, with everything else plugged in around it.

## Noweb

Again, I opted for Noweb, here, which may differ from other system.  The Noweb name riffs on Web---a long story where early literate programming setups each assumed its own preferred programming language, so Noweb brings literate programming to "no language"---and so the verbs/commands have a *no*-prefix.

### Making It Compile/Run

The prefix gives us `notangle`, which extracts the (traditional) code from the literate program.

Like I mentioned earlier, I can only remember this as tangling undoing the careful work of organizing the literate program, so that you get something compiler- or interpreter-friendly.  It takes a pile of options, but I'll hit the few that I find interesting.

- `-R`chunk - identifies the root chunk, if you didn't call yours `*`.
- `-L`format - provides a format for line-number directives for debuggers, if your compiler/interpreter supports such a thing, so that errors point to lines in the original (literate) source.
- `-filter `<command> - includes the filter in the pipeline for processing the files.

I haven't looked at filters, yet, but apparently they let a project hook into the tangling process to do things like automatically parse out variable declarations---so that the code doesn't need the `@ %def ...` comments---or modify the output files.

You also have the (weird, if you ask me) option of turning the comment chunks into comments in the tangled code, with options for different language styles and maximum line widths.  It also has options to handle tab characters in the source, but I assume that nobody really cares about that.

### Producing the Version for Reading

Meanwhile, `noweave` creates the document for publication.  And it also has a bunch of options.

- You can output using `-latex`, `-tex`, `-html`, or `-troff`.
- `-n` - this drops the full-document wrapper, in cases where the output will get embedded into something more significant.
- `-filter <command>` - runs the command before converting the code to its output format to add more complex processing.
- `-delay` - skips the page headers until after the first documentation chunk; this requires the final documentation chunk to include a TeX `enddocument` command or the equivalent.
- `-x` - enables cross-referencing and indexing.
- `-index` - does everything done by `-x`, but also includes the manual definitions (`@ %def`) mentioned before.
- `-autodefs` tries to catch definitions, if Noweb can parse the language, with the list of usable languages reported with `-showautodefs`.

Again, I haven't looked at the filters, but see references to handling declarations in an unsupported language, adjusting the output for a certain purpose, and so forth.

Presumably, `noweave` doesn't care what you call your root chunk because it renders each chunk in the order that the code lists them.

It also has tab configuration, LaTeX-specific header options, hooks to change the markup style, and so forth.

## Example

To see this put together, I'll also walk through an example of my own, which will have the funny effect of having a program styled with verbose design descriptions in between code sections interrupted for even more descriptions...

This adapts the code for the blog plugin that I wrote to [construct Wikipedia links](https://codeberg.org/jcolag/entropy-arbitrage-code/src/branch/main/_plugins/wiki.rb) in case I needed to shift away from Wikipedia-proper during their labor dispute.  I should also note that this technically makes for a bad example in a significant way, because I wrote the code previously, and then tried to reconstruct it as a literate program, so I didn't lead with the idea of presenting the design, making the comments largely bogus.  And I also won't manage the plugin this way, since I don't see a convenient way of convincing Jekyll to call `notangle` to get plugin code.

Regardless, I chose to start with a top-level "explain this project" comment.

```
@ Concept:

This Jekyll plugin hedges against the possibility of prolonged
problems with Wikipedia or the Wikimedia Foundation more
broadly.  As inputs, it takes a Wikipedia ID, the text to
render, and the language-version of Wikipedia to use.  It then
uses a URL template to create the target Wikipedia URL, with
the possibility of altering the template to direct traffic to
a safer mirror.

It originated during the Wikimedia Foundation's resistance to
its employees unionizing.  The dispute has ended with the
acceptance of the union(s), so it made sense to have a way to
make sure that the blog doesn't cross a picket line.
```

Next, I created a code chunk for the [REUSE](https://reuse.software/)-compliant licensing information.

```
<<Licensing>>=
# SPDX-FileCopyrightText: 2020 John Colagioia <john@colagioia.net>
#
# SPDX-License-Identifier: AGPL-3.0-or-later
```

If REUSE seems mystifying to you, I'll try to put together a post for that soon.

Ruby prefers frozen string literals---storing quoted text in a way that nothing in the program can modify it---so directives like that also get a chunk.

```
<<Directives>>=
# frozen_string_literal: true
```

Now we can get to one of the more interesting aspects of Literate Programming.  We can jump around the program to present the most useful things first.  And yes, that does mean that I should probably dump those headings later in the file, because nobody needs to read boilerplate up-front...except for the licensing information, since I provide it *for the purpose* of making it discoverable.

What part of this project has the highest importance?  If you look at nothing else in the code, you'd want to look at formatting the URL to Wikipedia.  Everything else supports getting here, and if someone needs to change the plugin to point at a Wikipedia mirror, the change happens at that point.

```
@ The Template:

Update the following to change from Wikipedia to one of its
mirrors.  Wikiless and Wikimili both seem up-to-date and
possible viable alternatives, though they will require
different URL formats.

It requires the [[@lang]], [[@page]], and [[@text]] global
variables to have settings from elsewhere.

<<Template>>=
"<a href='https://#{@lang}.wikipedia.org/wiki/#{@page}'>#{@text}</a>"
@
```

The empty comment at the end prevents extra blank lines from getting into the output files.  I could have put the entire next comment chunk there, but that seems more difficult to read.

Moving on, if you wanted the next-most-important piece of the plugin, you'd head for identifying the three inputs to the URL template, the page ID, the display text, and the language.

```
@ Handle the Input Parsing:

The following identifies the page, display-text, and language
requested when using the plugin.  It will assume
English-language Wikipedia (or mirror) by default.  And if it
can only find one argument, it assumes that the page ID looks
like the intended display name of the page, but with underscore
characters ([[_]]) replacing the spaces.

<<Parse>>=
page, text, lang = text.split '|'

unless text
  text = page.strip
  page = page.strip.gsub(' ', '_')
end

lang ||= 'en'
@ %def page, text, lang
```

This section ends by telling Noweb that it defines three variables that might appear somewhere else.

Notice that we didn't provide a full Ruby function to get the three pieces of information, only its core logic.  That gives us the flexibility to separate that potential target of maintenance from the function itself, which we have next, the `parse()` method.

```
@ Package the Parsed Arguments:

Here, we create the function to take the parsed arguments
(above) and bundle them for the main program to do what it
needs.

<<Arguments>>=
def parse(text)
  return unless text.is_a? String

  <<Parse>>
  [CGI.escape(CGI.unescape(page)).gsub('+', ' '), text, lang.strip]
end
@ %def parse
```

And we indicate that this section defines that function.

Notice that this chunk uses the `<<Parse>>` chunk.  And by the way, it pleased me to realize---I can't find this mentioned anywhere in the documentation---indenting the chunk name indents the full chunk in the output, as if I did it by hand.

Likewise, we can add the `render()` method that uses the URL template.

```
@ Rendering:

We need to apply the arguments to the URL template.

The unused parameter [[_context]] serves as a reminder that
the plugin may, one day, want to use Markdown to style the
display text for more general use than the plugin currently
gets.

<<Render>>=
def render(_context)
  <<Template>>
end
@ %def render
```

We also need the entry-point method, `initialize()`, which calls the earlier parsing method.

```
@ Main Code:

Generally speaking, the [[initialize()]] method doesn't do
much, but we need it to parse the information fed to the
plugin and assign it to global variables.

<<Initialize>>=
def initialize(tag_name, text, parse_context)
  super
  @page, @text, @lang = parse text
end
@ %def @page, @text, @lang, initialize
```

And now we pull everything together to create the tag's class, along with the licensing, directives, and registration boilerplate.

```
@ The Root:

We have more boilerplate to pull everything together.

<<Main>>=
<<Licensing>>
<<Directives>>
class WikiInlineTag < Liquid::Tag
  <<Initialize>>

  <<Render>>

  <<Arguments>>
end
Liquid::Template.register_tag('wiki', WikiInlineTag)
@ %def WikiInlineTag
```

I ran `notangle` to produce the original code.

```console
notangle -RMain wiki.rb.nw > wiki.rb
```

And again, it all has its proper indentation, and I can't distinguish the tangled version from the Ruby code in the blog's repository.

Meanwhile, `noweave` exports the full report, and then I needed to jump through hoops to turn it into a PDF.

```console
noweave -latex -index wiki.rb.nw > wiki.tex
latex wiki.tex      # This produces wiki.dvi
dvipdfm wiki.dvi    # This produces wiki.pdf
```

Other than needing two conversion steps, weaving only really stumbled because its indexing doesn't understand Ruby well enough to identify other uses of the variables.  But we do have a PDF to review.

It takes some getting used to reading it---harder in the tiny window above, so you might want to download the PDF---but it doesn't look bad.  I'd also call HTML acceptable, *except* that it doesn't know to change paragraphs, so unless you explicitly insert `<p></p>` tags everywhere, each comment block gets squashed into a single paragraph.

Overall, I like it.  The process, I mean.  My opinion of the actual formatting of the document doesn't really matter.

Granted, I don't see myself updating old projects like I did for the example.  And for small programs, this seems like overkill, especially for pieces that we wouldn't expect people to need to learn quickly.  However, for a new, big project that could use a lot of hands, I can see how this sort of discipline (and the right organization of chunks) could improve maintainability massively.

In particular, you have two approaches to navigating.  You can take the literary approach by starting at the beginning of the document and working through, but you can also find the root chunk and follow the layout of the program from there, as if reading the conventional code, but separated more intelligently.
